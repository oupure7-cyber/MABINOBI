# AI_Mabinogi — 마비노비 (MabiNobi)

마비노기 모바일 공식 **AI 커넥터** 기능을 활용해, 허용된 범위 내에서 반복적인 게임 동작(채집/제작/정보조회 등)을 자동으로 요청해주는 제어 프로그램(앱 이름: **마비노비**, "마비노기"+"노비" — 시키는 대로 게임 잔심부름을 대신 해주는 존재라는 말장난)을 만들기 위한 프로젝트.

## 배경

넥슨은 2026년 9월, PC 버전 마비노기 모바일에서 Claude Code / Cursor / Gemini CLI 등 로컬 AI 도구와 게임 클라이언트를 연결해 채팅·채집·제작·가공 등을 대화형으로 요청할 수 있는 **AI 커넥터** 기능을 공식 출시했다. 이 프로젝트는 그 공식 기능을 기반으로, 사용자가 매번 대화로 요청하지 않아도 원하는 동작이 자동으로 수행되도록 하는 제어 프로그램을 만드는 것을 목표로 한다.

공식 기능 요약: [81_GUIDE_MD/마비노기_모바일_AI_커넥터_가이드.md](81_GUIDE_MD/마비노기_모바일_AI_커넥터_가이드.md)

### 2026-09-20 로컬 개발판

- **생산 대기 중 재료 준비**: 현재 제작 목표에 필요한 가공 수량을 계산해 시설의 빈 칸에 연속 등록합니다. 보유량과 이미 생산 중인 예상 수량을 함께 반영하며, 필요한 건수가 적으면 빈 칸을 채우기 위해 불필요한 가공을 추가하지 않습니다. 같은 시설의 다른 품목과 회수 대기 작업도 점유 칸으로 계산합니다. 생산 중에는 다른 부족 재료의 채집·하위 제작·시설 등록을 계속하고, 수행 가능한 준비 작업이 없을 때만 완료를 기다립니다. 캐릭터가 수행하는 명령은 순서대로 실행하며 시설 생산만 함께 진행됩니다. 전체 작업 대기열의 순서는 유지합니다.

- **소모품·생활 아이템 목록 보완**: 사용자 스크린샷에 표시된 회복/강화/염색약/기타약품/기타음식/마법유탄/일반재료/캠프파이어/기타아이템의 고유 이름 96종을 기본 제작 목록에 등록했습니다. 게임 연결 전에도 보이며, 연결 후에는 게임에서 받은 정확한 이름·생산량·재료 조건을 사용합니다. 스크린샷에는 재료 정보가 없어 필요 재료를 임의로 넣지 않았습니다.
- **동명 제작법 자동 비교**: 같은 이름의 재료·제작법이 여러 개여도 그 이유만으로 중단하지 않습니다. 현재 제작 가능 여부, 부족 재료의 자동 채집·가공·제작 경로, 목표 수량에 맞는 생산량, 생산량 대비 준비할 재료를 비교합니다. 실제 시세·희귀도는 공개 정보가 없어 최저 비용을 보장하지 않습니다. 서로 대체 가능한 제작법의 재료를 합쳐 준비하지 않으며, 모든 대안 정보는 목록에 보존합니다. 커넥터가 이름으로만 실행을 지정하므로 게임 내부의 특정 제작법을 강제하지는 못합니다. 실행 후 재고 증가량이 확인된 후보 생산량과 맞는지 검증해 완료 수량을 갱신하고, 생산 중 예상량도 회수 후 실제 재고로 다시 계산합니다. 알려진 다른 제작법이 남은 목표보다 많이 생산할 수 있거나 실제 결과가 불명확하면 추가 소비 전에 안내합니다.

- **제작**: 게임 연결 후 `제작 목록 동기화`로 커넥터가 제공하는 전체 제작 목록을 가져옵니다. 목표 수량을 직접 입력하거나 화살표로 조절하고, 오른쪽 대기열로 드래그한 뒤 시작합니다. 시작 전에는 대기열에서도 수량을 바꿀 수 있습니다.
- **재료 준비**: 확인된 부족 재료를 채집하거나 중간 재료를 제작·시설 가공하고, 완료된 생산물을 회수한 뒤 최종 제작을 수행합니다. 공식 커넥터는 현재 부족한 1회분 재료만 알려주므로, 확인된 재료는 남은 목표분을 먼저 확보하고 매 제작 직전 조건을 재확인합니다. 전체 재료의 총 필요량을 사전에 확정하지는 못합니다. 지원 경로가 없는 재료나 레벨·잠금 조건은 이유를 표시하고 멈춥니다.
- **정확한 수량**: 1회 생산량의 배수만 실행합니다. 일시정지는 이미 시작한 요청이 끝난 뒤 적용되며 앱을 켜 둔 동안 완료량과 생산 대기 상태를 보존합니다. 결과를 확인하지 못한 동작은 중복 소비를 막기 위해 자동 재실행하지 않습니다. 앱 종료 후 대기열 복원은 지원하지 않습니다.
- **무한가공소**: 재료 보유량을 2열로 압축하고 시설별 7칸 상태를 표시합니다. 가공/대기와 회수 가능한 슬롯을 구분하며, 슬롯 수를 시간 진행률처럼 표시하지 않습니다.

## 원격 오버레이 문제 기록 (2026-09-20)

아래는 통합 전 원격 구현의 문제 기록입니다. 2026-09-21 통합판은 기존 진행 오버레이와 환경 표시가 같은 게임 창 좌표 변환을 사용하며, 환경 조회를 별도 작업 스레드로 옮겼습니다. 실제 게임과 사용자 화면 배율에서의 재확인은 필요합니다.

`app/dashboard/overlay.py`(인게임 오버레이 HUD) 관련해서 사용자가 실제 플레이 중 확인한, 아직 못 고친 문제 두 가지:

1. **오버레이 위치가 화면 비율이 안 맞아 계속 어긋남.** placeholder 텍스트 크기로 위치를 계산하던 버그는 고정 패널 크기(`PANEL_SIZE`)로 한 번 고쳤지만, 사용자 실측에서 여전히 위치가 틀어짐 — 이번엔 화면 "비율" 문제로 보고됨. 유력한 원인 후보: Windows DPI 스케일링. `overlay.py`는 `ctypes`의 `GetClientRect`/`ClientToScreen`으로 게임 창 좌표를 얻는데 이건 **물리 픽셀** 기준이고, Qt(`self.move()`)는 앱이 DPI-aware로 표시되는 방식에 따라 **논리 픽셀**(스케일링 적용됨) 좌표계를 쓸 수 있음 — 사용자 화면의 배율이 100%가 아니면 두 좌표계가 어긋나서 위치가 화면 비율(해상도)에 비례해 밀리는 것처럼 보일 수 있음. 개발 확인 머신은 96 DPI(100%)라 이 문제가 재현되지 않았음 — 사용자 실제 디스플레이의 배율(디스플레이 설정 → 배율 및 레이아웃)부터 확인하고, `QGuiApplication`의 `AA_EnableHighDpiScaling`/`devicePixelRatio()` 처리를 좌표 변환에 반영해야 할 가능성이 높음.
2. **오버레이가 refresh되지 않는 것처럼 보임.** `refresh_data()`는 `try_run_cli`(논블로킹)를 쓰기 때문에, 그 순간 CLI 락이 다른 곳(JOB 워커, 2초 주기 캐릭터 감지 폴링)에 잡혀있으면 조용히 스킵되고 이전 값을 계속 보여준다(의도된 동작이지만 체감상 "안 멈추는 것 같다"로 보일 수 있음). `10_RESEARCH/04_cli_getter_latency_2026-09-20.md`에 각 getter 호출의 실측 latency(순차 20회 평균, 전체 평균 ~124ms/call)를 기록해뒀으니, 오버레이의 `TRACK_INTERVAL_MS`(현재 500ms)를 이 수치와 캐릭터 감지 폴링 주기(2000ms)를 감안해 재검토할 것 — 500ms 틱마다 두 패널(가공+환경) 몫으로 CLI 호출 2번(순수 latency만 합쳐도 ~227ms)을 쓰고 있어서 다른 폴링과 자주 충돌해 스킵될 여지가 큼.
